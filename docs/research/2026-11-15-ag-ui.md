## What AG-UI is

An event protocol between an agent backend and a user-facing application. The application POSTs one
`RunAgentInput` (thread id, run id, the whole message list, the tools the page offers, context, state, resume
answers); the agent answers with a stream of typed JSON events for that one run, ending in `RUN_FINISHED` or
`RUN_ERROR`. It has had a written, normative 1.0 specification since this autumn: JSON Schema in
`spec/1.0/schema.json` (with conformance fixtures in `spec/1.0/fixtures/`), prose in `docs/spec/1.0/`, and before
that "0.x defined shapes; behaviour lived in the TypeScript client" (`docs/spec/1.0/changelog.mdx:12-18`).
`@ag-ui/core` is at 1.0.4 (`sdks/typescript/packages/core/package.json`). Releases are cut every one to three days
(`gh release list`: 2026-11-02, 03, 05, 06, 09, 10, 12, 13).

### Events (1.0)

Listed from `spec/1.0/schema.json`; behaviour in `docs/spec/1.0/events/`.

| Group | Events | Notes |
|---|---|---|
| Lifecycle | `RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`, `STEP_STARTED`, `STEP_FINISHED` | A stream opens with `RUN_STARTED` or `RUN_ERROR`; `RUN_FINISHED.outcome` is success, interrupt or cancelled; `usage` per provider and model with cache and reasoning parts (`lifecycle.mdx:12-210`). Several runs may follow each other on one stream, "a replayed thread is the common case" (`lifecycle.mdx:190`) |
| Text | `TEXT_MESSAGE_START`, `_CONTENT`, `_END`, `_CHUNK` | start/delta/end triad by `messageId`; chunk is the shorthand (`text-messages.mdx`) |
| Tools | `TOOL_CALL_START`, `_ARGS`, `_END`, `_CHUNK`, `_RESULT` | arguments stream as deltas; result is its own event (`tool-calls.mdx`) |
| Reasoning | `REASONING_START`, `REASONING_MESSAGE_START/CONTENT/END/CHUNK`, `REASONING_END`, `REASONING_ENCRYPTED_VALUE` | `reasoning.mdx` |
| State | `STATE_SNAPSHOT`, `STATE_DELTA` (RFC 6902), `MESSAGES_SNAPSHOT` | a messages snapshot is "the complete set of messages the producer owns"; held messages absent from it are dropped (`state.mdx:28-52`) |
| Activity | `ACTIVITY_SNAPSHOT`, `ACTIVITY_DELTA` | client-only rows of role `activity` with an open `activityType`, replaced by `messageId` (`activity.mdx`) |
| Subagents | `SUBAGENT_STARTED`, `_FINISHED`, `_ERROR`; `subagentRunId` on events | `subagents.mdx` |
| Pass-through | `RAW`, `CUSTOM` | `passthrough.mdx` |

### Transport

HTTP POST of the input, answered by Server-Sent Events (one event per `data:` frame; `event:` and `id:` are
ignored; comment lines are allowed); a binary protobuf binding is optional (`docs/spec/1.0/basic/transports/`). Other
channels such as WebSockets are allowed if they keep the event model (`transports/index.mdx`, "Custom transports").
"The binding has no stream resumption: SSE's `Last-Event-ID` mechanism is not used, and a broken stream cannot be
re-entered. Re-running is a new run" (`transports/http-sse.mdx`, "No resumption"). The TypeScript client's
`connectAgent()` (re-attach to a thread) throws unless a subclass implements `connect()`; `HttpAgent` does not
(`sdks/typescript/packages/client/src/agent/agent.ts:440-450`, `http.ts`).

### Frontend tools and approvals

"The protocol has no mid-run channel from the consumer" (`tool-calls.mdx:155-160`). So:

- A frontend tool (one in `RunAgentInput.tools`) is called by the agent, which then ends the run with success and
  `pendingToolCallIds`; the page runs it and sends the result in the next run's messages (`tool-calls.mdx:155-218`).
- An approval or question ends the run with the interrupt outcome carrying `Interrupt` objects (`reason`,
  `message`, `toolCallId`, `responseSchema`, `expiresAt`); the next run carries `resume` entries answering every one
  (`docs/spec/1.0/basic/patterns/interrupt-resume.mdx`).

### Versioning

`RunAgentInput.protocolVersion` and `RUN_STARTED.protocolVersion`, each side its own; additions are safe, unknown
fields are stripped with a warning, lossy downgrades must warn, retired shapes are translated by middleware
(`docs/spec/1.0/basic/versioning.mdx`).

## Hypomnema's chat stream today

`GET /chats/{id}/stream` (`api/openapi.yaml`, `StreamChat`; `internal/controlplane/clientapi/chats.go:302-490`) is
one long-lived SSE stream per chat, not per turn. It sends `state` first, then each kept message after the cursor
as `message` with its `seq` as the SSE id, then live frames from pi held only in memory
(`internal/controlplane/coordinator/live.go`): `reset`, `delta` `{kind, index, delta}`, `tool`
`{phase, id, name, args}`, `state` `{working}`, `usage` `{context_window, tokens, percent}`
(`coordinator/usage.go`). A kept message replaces what the live frames showed. A reconnect resumes with
`Last-Event-ID`; a revised artifact's message is sent again (`sendRevised`). The owner's message goes separately by
`POST /chats/{id}/messages` and may queue while pi works; wake-ups from Runs start turns with no request from the
page. Approvals are not in the stream: the web polls `GET /approvals` (`web/src/features/approvals/use-approvals.ts`).
The web reads it in `web/src/features/chat/use-chat-stream.ts` into its own reducer (`chat-state.ts`).

## Mapping

| Hypomnema | Nearest AG-UI | Fit |
|---|---|---|
| `state {working: true/false}` | `RUN_STARTED` / `RUN_FINISHED` | close; AG-UI needs the input that opened the run |
| `reset` | `TEXT_MESSAGE_START` with a new `messageId` | partial: AG-UI has no "drop what was shown" |
| `delta` kind text / thinking | `TEXT_MESSAGE_CONTENT` / `REASONING_MESSAGE_CONTENT` | close (`index` becomes a message id) |
| `tool` start (name, whole args) | `TOOL_CALL_START` + one `TOOL_CALL_ARGS` + `TOOL_CALL_END` | close |
| `tool` end | none; the result arrives in the kept message | — |
| `message` role tool (`tool_result` part) | `TOOL_CALL_RESULT` | close |
| `message` owner / coordinator (kept, replaces preview) | `MESSAGES_SNAPSHOT` | partial: a snapshot is the complete set, Hypomnema sends pages after a cursor |
| `message` kind `failed` / `stopped` | `RUN_ERROR` / `RUN_FINISHED` outcome cancelled | close |
| `message` kind `wake`, `approval` | `ACTIVITY_SNAPSHOT` or `CUSTOM` | none standard |
| `message` kind `artifact`, re-sent on a new revision | `ACTIVITY_SNAPSHOT` replacing by `messageId` | good |
| `usage` (context window fill) | `RUN_FINISHED.usage` is tokens spent, not fill | none; `CUSTOM` |
| Approvals (polled, answered while pi goes on) | interrupt outcome + `resume` | different model: the run must end |
| Runs and Tasks of the chat | `SUBAGENT_*`, `parentRunId` | partial |
| `Last-Event-ID` resume | none ("No resumption") | missing in AG-UI |

AG-UI has, Hypomnema lacks: shared state (`STATE_*`), frontend tools in the input, context items, streamed tool
arguments, steps, subagent attribution, token usage per run with cache parts, encrypted reasoning, a version
handshake, a schema with conformance fixtures, a protobuf binding.

Hypomnema has, AG-UI lacks: one stream per chat that several viewers follow and resume by `Last-Event-ID`;
history kept by the server rather than sent by the page on every run; messages sent while a turn runs (the queue);
turns started by the server (wake-ups); approvals answered without ending the turn; the context-window meter;
artifact revisions; the Bot's tool display filter.

## Recommendation

Do not adopt AG-UI for the chat stream now; reconsider only when an outside AG-UI client (CopilotKit, a Slack
channel through CopilotKit's SDK) has to talk to a Hypomnema Bot, and then do what Omnara does: an adapter beside
the stream, not a replacement.

Reasons, weighed by complexity:

- **Different shape.** AG-UI is request-scoped: the page owns the transcript, POSTs it each run, the stream ends
  with the run and cannot be resumed. Hypomnema's chat is server-owned and long-lived: turns start without the page
  (wake-ups), messages queue mid-turn, several viewers watch, reconnects resume by seq. Speaking AG-UI means either
  giving those up or bending it (a custom long stream, every system row as `CUSTOM`), which keeps two vocabularies
  that must agree with the kept messages: one more state to keep consistent and one more failure mode on
  reconnect. (Inference from the specs above.)
- **Approvals do not fit.** AG-UI ends a run to ask and resumes in a new run; in Hypomnema the request that asked is held
  (up to 100 s) inside pi's open turn while the owner answers a card the web polls (`ARCHITECTURE.md`, "An
  Approval"; `2026-11-11-service-proxy-and-approvals.md`). Mapping one onto the other changes when a turn is over.
- **What it would buy is available without it.** The concrete gain would be using a ready chat runtime unchanged.
  assistant-ui's components work over any runtime, including an external store fed by the current stream
  (`.tmp/assistant-ui/packages/`); CopilotKit's components need AG-UI but no reference Hypomnema follows uses
  CopilotKit. Omnara, the closest reference, kept its own API and was given an adapter.
- **Churn.** The 1.0 specification is new and releases come every few days; the Go SDK is a community one.

What to take from it now, without adopting it: its token-usage accounting (inputs include cache reads and writes as
named parts; absent is not zero; `lifecycle.mdx:132-170`) if the chat ever reports cost, and its rule that an
artifact-like row is replaced by id (`ACTIVITY_SNAPSHOT`), which matches what `sendRevised` already does.
