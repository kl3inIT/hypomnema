# Web Push to the owner's devices

Issue #1047, 2026-11-21. The owner works in Orca on his laptop and in the web app on his iPhone, added to the Home
Screen. Nothing told him when something waited on him unless a Hypomnema tab was open: on 2026-11-21 he learned of
a worker's question only by looking at the chat. An Orca plugin was weighed and left for later: it would be a second
UI over an Inbox still being built (#838). Web Push reaches the desktop browser and the iPhone Home Screen app
(iOS 16.4+) with one mechanism.

Checked on main before the design (2026-11-21): `web/public/manifest.webmanifest` exists (`display: standalone`), so
the iPhone installs the app; there was no service worker and no push sending. The API already had what decides
"waits on you": `/questions`, `/approvals`, `/connection-requests`, `/inbox/needs-you` and `/events/stream`.

More read in the code while building:

- OpenClaw serves its `sw.js` with `Cache-Control: no-cache`, never immutable
  (`src/gateway/control-ui-conditional.http.test.ts:326`), so the browser takes a new worker at once. Hypomnema
  serves `sw.js` the same way, at the root so its scope is the whole app; the page's Content-Security-Policy
  (`script-src 'self'`, which `worker-src` falls back to) already allows it.
- Coder re-subscribes from the service worker on `pushsubscriptionchange` and posts the new keys
  (`site/src/serviceWorker.ts`, `handlePushSubscriptionChange`), the iOS reinstall case. Hypomnema does the same; it
  does not delete the old endpoint from the worker (it does not know its id), which the push service's 410 removes
  later.
- Coder registers the worker from the app's entry (`site/src/index.tsx:24`) and asks `Notification.requestPermission`
  before `pushManager.subscribe`, so a blocked site gets a plain message (`site/src/contexts/useWebpushNotifications.ts`).
- OpenClaw names a push by a tag per item and sends its Topic as the first 32 characters of the base64url SHA-256 of
  the tag (`src/gateway/event-web-push.ts:283-305`); TTL 300 for every event push (`EVENT_PUSH_TTL_SECONDS`, line 42).
- OpenClaw fences a push whose item ended before it was sent (`mention.isCurrent()` in `event-web-push.ts`); Hypomnema
  reads each queued item again when it sends and drops one that no longer waits.
- OpenClaw's Settings put Notifications in a group "Preferences" (`ui/src/app-navigation.ts`,
  `SETTINGS_NAVIGATION_GROUPS`).
- Coder's sender reads at most 64 KiB of a push service's answer and gives up after 30 s (`MaxResponseBodyBytes`,
  `pushRequestTimeout`). Its SSRF-safe dialer, which refuses private addresses, was left out: only the owner's own
  token may register an endpoint, and the owner already has terminals on the nodes.

## How it was built

What exists is in [ARCHITECTURE.md](../../ARCHITECTURE.md) (Web Push). Choices the design did not settle, each with
its source:

- "After commit, through the event subscriber" is a queue row (`push_outbox`) written in the item's own transaction
  and read by the sender when `orchestration.Subscribe` signals a commit: Second Bite's outbox. A question for the
  owner queues one when it is asked to him or forwarded to him (both wait on him).
- One TTL, 300 s, for the four kinds: OpenClaw uses it for every event push; the design named it for questions and
  Approvals and nothing else for the other two.
- "A few" retries are three tries in all, 1 s and 4 s apart, in the sender; a push still refused is dropped, as
  Coder drops what it cannot deliver.
- A to-do pushes when a Bot or the system adds one that needs the owner by the Inbox's needs-you predicate (in
  practice a proposal, or his own with a reply drafted); one he writes himself does not. The Inbox has no web page
  yet, so its push opens the chat it came from, else the start page.
- After review (PR #1050): the regenerate command deletes the subscriptions and keeps the new key in one
  transaction, as Coder's `RegenerateVAPIDKeys` (`coderd/webpush/webpush.go:534`); only a push for a chat is hidden
  when that chat has the focus, so the test push shows on Settings; a renewed subscription is kept only for an
  endpoint the control plane still lists, so a removed device stays removed (Coder's handler re-posts whatever the
  browser gives); a push's body is cut again after JSON encoding, which can grow a character to six bytes.
- Safari shows a Declarative Web Push message by itself when the service worker shows nothing (WebKit, "Meet
  Declarative Web Push"), so on an iPhone a push for the chat in view is not hidden. The design keeps the declarative
  form, which shows even when the worker does not run; Coder hides it because its payload is not declarative (its
  worker adds `navigate` to `showNotification`). Inferred from WebKit's contract, not tried on a device.
- Without an https public URL the control plane sends nothing: Apple refuses another VAPID subject, and a service
  worker needs a secure origin anyway.

Only a real device proves delivery to the iPhone Home Screen app; the tests use a fake push service over TLS and a
stubbed Push API in the browser.
